# Management-plane hardware startup

The MP detects local hardware at each boot. Installed platform modules declare
which MP identities they support and the ordered services that already own their
CP/DP hardware. CP and DP agents report results; neither selects the platform.
The WebUI and console read the MP controld status and do not initiate detection.

`ffn-hardware-boot.service` is a serialized MP execution worker. It runs after
management networking and controld, before configd applies committed settings:

1. Read the MP's numeric PCI inventory and DMI identity through `ffn_hwdetect`.
2. Match exactly one locally installed `boot.json`. Missing or ambiguous
   specialized-hardware support blocks startup; ordinary generic hosts retain
   their existing CPU-only startup. Hardware manifests and customer deployment
   settings are separate. Discovery never downloads or imports executable code.
3. Observe each existing service, starting only units that have not completed
   startup. Already-active services and completed oneshots are retained. CP/DP
   requests use provisioned SSH profiles with strict host-key checks.
4. Wait for fresh controld observations with matching CP/DP roles, platform,
   boot IDs and the module's required hardware readbacks. Stale reports and
   merely installed drivers are insufficient. A changed processor boot ID later
   makes the reported state degraded.
5. Let configd apply the saved running configuration. Hardware readiness does
   not claim Security/NAT policy acknowledgment or verified FE100 offload.

The state journal records every start intent before submitting it. An uncertain
or failed operation is not automatically replayed during the same MP boot.
There is no `restart`, reset, direct register write, port assignment or policy
creation in this worker. The existing platform owners retain their locks,
firmware validation and reset sequencing. Their underlying startup can initialize
hardware, so install this integration only with commissioned boot owners.

## Install on a commissioned MP

First install the matching core control gateway and CP/DP agents. Install the
platform's existing hardware/thermal/port services on their intended processors.
Provide a local JSON file containing these transport fields:

```json
{
  "cp": {"ssh_config": "/etc/ffn-ngfw/ssh-cp.conf", "host": "ffn-cp"},
  "dp": {"ssh_config": "/etc/ffn-ngfw/ssh-dp.conf", "host": "ffn-dp"}
}
```

The host aliases and files are examples of provisioning choices. The DP profile
must define its management path through the CP, trusted host keys and its local
credentials. No addresses, private keys, interfaces, VLANs or user configuration
are baked into the boot profile or generated by the installer.

```sh
sudo python3 image/install-hardware-boot.py \
  --platform /path/to/selected/platform --transports /path/to/transports.json
python3 /usr/local/lib/ffn/ffn_hardware_boot.py plan
```

For a commissioned board whose DMI lacks a model, `--enroll-hardware` explicitly
binds the selected module to the observed MP DMI/PCI fingerprint. Required PCI
identities still must match. A changed fingerprint requires review and enrollment;
a generic Cavium device alone never identifies a PA-5220.

Installation enables the MP boot worker for future startup and removes the
profile's independent MP boot-unit enablement, without stopping those units.
It adds a configd dependency on successful hardware startup. It does **not**
restart the current processors or services. The commissioned boot unit remains
installed and owns the actual processor initialization. Do not enable a second
independent boot/reset path for the same hardware. The installer backs up files
it replaces under `/var/backups/ffn/hardware-boot-*`.

## Images, status and recovery

The separate image downloader stages qualified release bundles on the MP.
This worker reports the verified offline cache status, and boots using the
locally commissioned service configuration. A failed Internet connection does
not replace or reset a working local boot image. Selecting and provisioning a
new kernel/root pair remains a separate image activation operation.

Read status with `show platform boot` on a supporting platform, or the root MP
command `python3 /usr/local/lib/ffn/ffn_hardware_boot.py status`.
The same data appears as `hardware_boot` in `state/control` and the authenticated
`/api/system/control` response, and in the Control Planes view. Detailed startup
logs are in `journalctl -u ffn-hardware-boot`. No browser credentials are used by
the boot worker or console transport.

If a step fails, later steps do not run and configd remains gated. Inspect the
named service and current CP/DP boot identities before recovery. Re-running the
worker cannot repeat an uncertain hardware start during that MP boot. A processor
restart after startup is reported as degraded and continues to use its existing
commissioned recovery/watchdog path; this service does not introduce automatic
reset loops or claim to requalify dataplane offload.

Tests: `python3 -m unittest discover -s tests -p test_hardware_boot.py`.
